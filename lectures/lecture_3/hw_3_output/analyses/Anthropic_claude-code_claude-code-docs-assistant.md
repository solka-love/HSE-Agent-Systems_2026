## Структура
1. **Введение / Определение роли** — объявляет ассистента помощником по документации Claude Code
2. **Scope (Область)** — описывает два продукта (Claude Code CLI и Claude Agent SDK) и границы ответственности
3. **Правила обработки запросов** — инструкции не отказывать из-за краткости/двусмысленности, не спрашивать уточнений на первом шаге, как обрабатывать код/ошибки без вопроса
4. **Language (Язык)** — отвечать на языке пользователя, использовать локаль пользователя в ссылках
5. **Query patterns (Паттерны запросов)** — детальные правила для запросов с `/`, голых имён фич, сторонних инструментов, цен, лимитов
6. **Agent SDK queries** — как отличать вопросы об Agent SDK от CLI и куда направлять
7. **Installation and error messages** — обширная таблица соответствия ошибок → страницы документации
8. **Walk through PATH problems step by step** — пошаговый протокол диагностики PATH
9. **Commands you can't find** — как реагировать на неизвестные команды
10. **Terminology** — правила использования терминов (CLI, command, non-interactive mode, subagent)
11. **Avoid false negatives** — не утверждать, что чего-то нет, если документация явно не говорит об этом
12. **Answering style** — стиль ответов: ссылка + краткое резюме

## Persona
Ассистент объявлен **документационным помощником** Claude Code — дружелюбным, проактивным и отзывчивым. Он — «primary support surface» (основная поверхность поддержки), поэтому настроен помогать, а не отклонять вопросы. Тон — helpful, patient, методичный. Чётко ограничен рамками документации Claude Code и Agent SDK, но при этом гибок в интерпретации запросов.

## Сильные стороны
- **Исключительно детальная обработка edge cases** — таблица соответствия ошибок → страницы документации, пошаговая диагностика PATH, обработка запросов без вопроса (паста кода/ошибки).
- **Гибкая маршрутизация запросов** — паттерны для `/команд», голых имён фич, сторонних инструментов, SDK vs CLI.
- **Правило «не отказывать»** — явный запрет на отклонение коротких, двусмысленных или неанглийских запросов.

## Слабые места
- **Нет описания инструментов (tools)** — промпт не объясняет, как ассистент должен получать содержимое документации (поиск, чтение страниц, индексация). Это делает оценку по критерию «Работа с инструментами» низкой.
- **Chain-of-thought только фрагментарно** — пошаговое мышление предписано только для диагностики PATH, но не для общего случая ответа.
- **Нет явного формата ответа** — хотя стиль описан («ссылка + одно предложение»), нет строгой структуры (JSON, markdown-шаблон).

## Что заимствовать
- **Таблица соответствия ошибок → действия** — мощный приём для любого support-промпта: конкретные строки ошибок маппятся на конкретные страницы/инструкции.
- **Правило «не спрашивай уточнений на первом шаге»** — снижает фрустрацию пользователя, заставляет ассистента делать обоснованное предположение.
- **Пошаговая диагностика (walk-through)** — «Diagnose in this order. Wait for the user's output between steps» — отличный пример структурированного CoT для поддержки.
