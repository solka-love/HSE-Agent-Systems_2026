## Структура
1. **YAML Frontmatter** — метаданные агента: имя (`statusline-setup`), сценарий использования (`whenToUse`), разрешённые инструменты (`[Read, Edit]`), модель (`sonnet`), цвет (`orange`)
2. **Определение роли** — декларация: «You are a status line setup agent for Claude Code», описание задачи — создание/обновление команды statusLine в настройках пользователя
3. **Инструкция по конвертации PS1** — пошаговая процедура: чтение shell-конфигов (4 файла по приоритету), извлечение PS1 через regex, преобразование escape-последовательностей в shell-команды, обработка ANSI-цветов через `printf`, удаление завершающих `$`/`>`
4. **Обработка отсутствия PS1** — guardrail: если PS1 не найден и пользователь не дал других инструкций — запросить дальнейшие указания
5. **Спецификация входного JSON (stdin)** — полная схема данных, передаваемых в statusLine-команду: session_id, prompt_id, cwd, model, workspace, version, output_style, context_window, effort, thinking, rate_limits, prompt_cache, vim, agent, pr, worktree
6. **Few-shot примеры bash-команд с jq** — 10+ примеров извлечения полей из JSON: display_name, current_dir, remaining_percentage, rate_limits, prompt_cache (cold detection), repo, PR/MR
7. **Инструкция по сохранению скрипта** — рекомендация сохранять длинные команды в `~/.claude/statusline-command.sh`
8. **Инструкция по обновлению settings.json** — как прописать statusLine в `~/.claude/settings.json` (с учётом symlink)
9. **Guidelines / завершающие указания** — сохранять существующие настройки, возвращать сводку, информировать родительский агент о необходимости использовать этого агента для дальнейших изменений status line

## Persona
Ассистент объявлен как узкоспециализированный агент («status line setup agent for Claude Code») без дополнительных черт характера или тона. Роль сугубо функциональна: конвертировать PS1, создавать/обновлять конфигурацию statusLine. Тон нейтрально-инструкционный, без эмоциональной окраски. Рамки идентичности заданы через frontmatter (имя, модель, цвет) и явное указание, что этот агент должен использоваться для всех дальнейших изменений status line.

## Сильные стороны
- **Исключительно богатые few-shot примеры** — 10+ готовых bash-команд с jq для каждого поля JSON-входа. Это лучшая практика: разработчику не нужно разбираться в структуре JSON, он может скопировать готовый сниппет.
- **Полная спецификация входных данных** — JSON-схема всех полей, передаваемых в statusLine-команду, с комментариями. Это устраняет неоднозначность.
- **Обработка краевых случаев** — symlink в settings.json, отсутствие PS1, удаление завершающих `$`/`>`, пропуск опциональных блокировок git.

## Слабые места
- **Отсутствие Chain-of-Thought** — агент не инструктирован проверять корректность сгенерированной команды перед записью, что может привести к поломке конфигурации.
- **Слабые guardrails** — нет явных запретов (например, «не удаляй существующие настройки, если не уверен»), нет проверки валидности JSON перед записью.
- **Нестрогий output format** — не указан точный шаблон ответа, что может привести к неконсистентным сводкам для родительского агента.

## Что заимствовать
- **Подход с полной JSON-схемой входных данных** — включение спецификации всех полей прямо в промпт устраняет догадки и ошибки парсинга.
- **Массовые few-shot примеры для каждого поля** — каждый значимый кусочек данных сопровождается готовой bash-командой; это резко снижает порог входа.
- **Механизм делегирования родительскому агенту** — финальная инструкция «inform the parent agent that this agent must be used for further changes» создаёт чёткий маршрут маршрутизации запросов.
