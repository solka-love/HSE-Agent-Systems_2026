2. **Введение: обзор runtime capabilities** — как декларировать capabilities, механизмы contract pin, смена версий, оммиссия и очистка

5. **capability: assets** — загрузка и хранение файлов (изображения, PDF, CSS/JS): лимиты, типы, организация-внутренние страницы
6. **capability: db** — JSON-документное realtime-хранилище: коллекции, документы, правила доступа, приватные viewer-документы, lease на запись
7. **capability: downloads** — предложение файла для скачивания пользователю с подтверждением
8. **capability: mcp** — вызов коннекторов claude.ai из страницы: watchTool, callTool, кэширование, error handling
9. **capability: permissions** — ленивый запрос согласия: state (без промпта), request (один диалог), обработка отказа
10. **capability: room** — realtime-присутствие: emit/on, presence, onPeers, ограничения персистентности
11. **capability: sample** — вызов Claude из страницы: input, onText, tools, images, modelTier, ошибки
12. **capability: self** — устаревший алиас для artifact (обратная совместимость)
13. **Connectors и MCP-серверы** — префикс `mcp__claude_ai_*`, получение списка через curl в CI/hermetic-сессиях
14. **Call contract и TypeScript типы** — ссылки на `.d.ts` файлы, требование наблюдать реальный запрос перед публикацией, запрет на встраивание наблюдаемых данных

## Persona
Документ не задаёт persona ассистента-собеседника в классическом смысле. Это **skill-файл для агента**, который пишет Artifact-страницы. Persona — технический документатор: строгий, детальный, категоричный в запретах. Тон нейтрально-технический, без эмоций. Главная рамка: «ты — разработчик runtime-функциональности, который обязан понимать каждую capability, её ошибки и ограничения, и никогда не угадывать API вслепую».

## Сильные стороны
- **Исчерпывающая документация каждого инструмента** — для каждой capability даны: назначение, API, лимиты, типы ошибок, антипаттерны. Это эталон технической спецификации.
- **Категоричные guardrails** — множество чётких запретов с формулировками "never...", которые явно отсекают нежелательное поведение агента.
- **Чёткое разделение ответственности** — когда использовать `artifact` vs `db`, когда `room` vs `db` — прописано явно и недвусмысленно.

## Слабые места
- **Нет few-shot примеров** — ни одного примера кода «вход → выход». Агенту приходится собирать сигнатуру из prose-описания.
- **Нет цепочки рассуждений (CoT)** — не указано, как агенту выбирать между capabilities, в каком порядке их декларировать, как дебажить проблемы.
- **Нет persona-тона** — документ сугубо технический, без personality, что снижает вовлекаемость.
- **Нет схемы разрешения конфликтов** — сказано, что `conflict` рутиный, но не объяснено, как агенту обрабатывать его в своём коде.

## Что заимствовать
- **Структура «описание → API → лимиты → ошибки → антипаттерны»** — отличный формат для технической документации инструментов, пригодный для любых промптов с множеством tools.
- **Формулировки категоричных запретов** — `"never X"`, `"do not Y"` — эффективно предотвращают нежелательное поведение агента.
- **Механизм мемоизации** — `"Awaiting use() again is free (memoized)"` — хороший приём оптимизации для любого API.
- **Принцип "branch on null / design for absence"** — требование обрабатывать недоступность capability до её использования.
