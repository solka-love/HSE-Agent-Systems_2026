## Шаг 1 — Fixed-size chunking

**Описание**: Базовый RAG: PDF → docling (markdown) → очистка → `fixed_size_chunking` → эмбеддинги → LanceDB → векторный поиск top-3 → LLM.

**Обоснование**: Самая простая рабочая версия — точка отсчёта для всех улучшений.

**Что изменилось**:

- Написаны `data_preporation.py`, `embedder.py`, `lance_db.py`, `retriever.py`, `agent.py`
- `CharacterTextSplitter` по разделителю `\n\n`, chunk_size 1000, overlap 200

**Метрики**:

| Метрика | Значение |
| -------------- | ---------------- |
| Precision@K    | 0.2689           |
| Recall@K       | 0.7378           |
| F1@K           | 0.3884           |
| MRR            | 0.6256           |
| MAP            | 0.6013           |
| NDCG@K         | 0.6423           |
| Faithfulness   | 0.7021           |

**Вывод**: Нужный фрагмент в top-3 находится в ~74% случаев, но Precision низкий: вернули 3 чанка, а эталон у 140 из 150 вопросов один.

## Шаг 2 — Semantic chunking

**Описание**: Переход с `fixed_size_chunking` на `semantic_chunking` (`RecursiveCharacterTextSplitter`).

**Обоснование**: `CharacterTextSplitter` режет только по пустым строкам и не разбивает абзац длиннее `chunk_size`. Таблицы и длинные абзацы из docling попадали в чанк целиком — максимальная длина чанка  символов при заданных 1000. Вектор такого чанка «размыт», и при top-3 контекст приближается к лимиту 6000 символов.

**Что изменилось**:

- Разделители по приоритету: `\n\n` → `\n` → `. ` →  → `""` — длинный абзац режется по предложениям
- chunk_size 500, overlap 100
- Секция документа сохраняется в метаданные (`section`), но в поиске пока не используется

**Метрики**:

| Метрика |   До | После | Дельта | Изменение |
| -------------- | -----: | ---------: | -----------: | -----------------: |
| Precision@K    | 0.2689 |     0.2867 |      +0.0178 |              +6.6% |
| Recall@K       | 0.7378 |     0.8156 |      +0.0778 |             +10.5% |
| F1@K           | 0.3884 |     0.4196 |      +0.0312 |              +8.0% |
| MRR            | 0.6256 |     0.7044 |      +0.0788 |             +12.6% |
| MAP            | 0.6013 |     0.6780 |      +0.0767 |             +12.8% |
| NDCG@K         | 0.6423 |     0.7196 |      +0.0773 |             +12.0% |
| Faithfulness   | 0.7021 |     0.7552 |      +0.0531 |              +7.6% |

**Вывод**: Помогло. Сильнее всего выросли MRR/NDCG (+12%) — нужный фрагмент чаще оказывается выше в выдаче: мелкие однородные чанки точнее матчатся с вопросом.

## Шаг 3 — Фильтр по метаданным (год отчёта)

**Описание**: Поиск ведётся только среди чанков того года, о котором спрашивают.

**Обоснование**: Отчёты 2019 и 2025 годов написаны похожими формулировками («индекс потребительской уверенности повысился на … п. п.»), и поиск доставал похожий фрагмент чужого года. `evaluation.py` засчитывает чанк с `year != document` как нерелевантный, даже если текст совпал. А LLM, получив чанки чужого года, отвечала «в контексте нет данных за 2025 год».

**Что изменилось**:

- Год извлекается из вопроса LLM-вызовом (structured output, JSON `{"year": 2019 | 2025 | null}`) с валидацией по списку доступных лет; при `null` фильтр не ставится
- В LanceDB: `.where("year = N", prefilter=True)` — сначала отбор по году, затем top-k среди них (иначе можно получить 0 чанков)

**Метрики**:

| Метрика |   До | После | Дельта | Изменение |
| -------------- | -----: | ---------: | -----------: | -----------------: |
| Precision@K    | 0.2867 |     0.3133 |      +0.0266 |              +9.3% |
| Recall@K       | 0.8156 |     0.8867 |      +0.0711 |              +8.7% |
| F1@K           | 0.4196 |     0.4573 |      +0.0377 |              +9.0% |
| MRR            | 0.7044 |     0.7967 |      +0.0923 |             +13.1% |
| MAP            | 0.6780 |     0.7678 |      +0.0898 |             +13.2% |
| NDCG@K         | 0.7196 |     0.8054 |      +0.0858 |             +11.9% |
| Faithfulness   | 0.7552 |     0.9037 |      +0.2485 |             +32.9% |

**Вывод**: Самый сильный шаг по Faithfulness: LLM перестала получать чанки чужого года и отказываться от ответа.  NDCG перешёл порог 0.75.

**Наблюдение**: Precision@K = 0.313 при потолке 0.333 для top-3 (у 140/150 вопросов один эталон, Precision = найденные / возвращённые). F1 при top-3 не может превысить 0.5 — следующий шаг: top_k = 1.

## Шаг 4 — top_k: 3 → 2 → 1

**Описание**: Абляция по числу возвращаемых чанков.

**Обоснование**: `evaluation.py` считает Precision как (релевантные / число возвращённых чанков), а у 140 из 150 вопросов ровно один эталонный фрагмент. Потолки F1 при идеальном поиске: 0.5 для top-3, 0.667 для top-2, 1.0 для top-1. На шаге 3 Precision был 0.313 при потолке 0.333, то есть дальнейшие улучшения поиска уже не могли поднять F1.

**Что изменилось**:

- `Retriever(top_k=...)` — прогон на трёх значениях, остальной пайплайн без изменений

**Метрики** (дельта — от top-3 к top-1):

| Метрика |  top-3 |  top-2 |  top-1 | Дельта | Изменение |
| -------------- | -----: | -----: | -----: | -----------: | -----------------: |
| Precision@K    | 0.3133 | 0.4200 | 0.7067 |      +0.3934 |            +125.6% |
| Recall@K       | 0.8867 | 0.8033 | 0.6789 |     −0.2078 |            −23.4% |
| F1@K           | 0.4573 | 0.5460 | 0.6867 |      +0.2294 |             +50.2% |
| MRR            | 0.7967 | 0.7733 | 0.7067 |     −0.0900 |            −11.3% |
| MAP            | 0.7678 | 0.7411 | 0.6789 |     −0.0889 |            −11.6% |
| NDCG@K         | 0.8054 | 0.7644 | 0.6848 |     −0.1206 |            −15.0% |
| Faithfulness   | 0.9037 | 0.8881 | 0.8828 |     −0.0209 |             −2.3% |

**Вывод**: Размен Precision на Recall. F1 растёт монотонно при уменьшении top_k, NDCG и MRR падают: при top-3 правильный чанк на 2–3 месте ещё приносил очки, при top-1 это промах. Recall при top-1 ограничен сверху ≈0.96 — у 10 вопросов по 2–3 эталонных фрагмента, одним чанком их не покрыть.

Дальше работаем с top_k = 1 и улучшаем ранжирование; top-2 оставлен как запасной вариант и будет перепроверен в конце.

**Наблюдение**: при top-1 Precision@K = MRR = доля вопросов с правильным чанком на первом месте — 0.7067, то есть 106 попаданий из 150. Теперь F1, NDCG и MRR зависят от одной величины, и следующие шаги поднимают их одновременно. Для F1 > 0.75 нужно ≈116 попаданий, для > 0.90 — ≈139.

## Шаг 6 — Окно соседей (small-to-big)

**Описание**: Поиск идёт по отдельным чанкам, а в выдачу попадает найденный чанк, склеенный с соседями ±1 в один фрагмент.

**Обоснование**: Чанк фиксированного размера обрывает мысль: начало фразы оказывается в предыдущем чанке, а число — в следующем. Поиск находит правильное место, но контекст для LLM неполный. Склейка соседей возвращает контекст целиком и при этом **не увеличивает число чанков** в `retrieved_chunks`, то есть не бьёт по Precision.

**Что изменилось**:

- `Retriever.expand(row)` — берёт `chunk_id ± WINDOW` и склеивает тексты в один
- `Retriever.retrive` отдаёт в `Chunk.text` расширенный текст, `chunk_id` остаётся от центрального чанка

**Метрики** (top_k = 3, как на шаге 5):

| Метрика |   До | После | Дельта | Изменение |
| -------------- | -----: | ---------: | -----------: | -----------------: |
| Precision@K    | 0.3156 |     0.3222 |      +0.0066 |              +2.1% |
| Recall@K       | 0.8933 |     0.9100 |      +0.0167 |              +1.9% |
| F1@K           | 0.4607 |     0.4700 |      +0.0093 |              +2.0% |
| MRR            | 0.8144 |     0.8411 |      +0.0267 |              +3.3% |
| MAP            | 0.7848 |     0.8193 |      +0.0345 |              +4.4% |
| NDCG@K         | 0.8199 |     0.8486 |      +0.0287 |              +3.5% |
| Faithfulness   | 0.7604 |     0.8490 |      +0.0886 |             +11.7% |

**Вывод**: Сработало по всем метрикам. Сильнее всего выросла Faithfulness (+11.7%): модель перестала отвечать «в контексте нет данных», получив обрезанный фрагмент. Precision@K = 0.3222 при потолке 0.3333 для top-3 — поиск практически упёрся в ограничение метрики, дальше нужен top-1.

**Ограничение**: окно ±1 выбрано осознанно. Метрика считает чанк релевантным при 30% общих токенов с эталоном, и чем длиннее фрагмент, тем выше шанс случайного совпадения. Расширение окна до ±3 дало бы рост метрик за счёт длины, а не качества поиска.
